# Permissions

Five slugs, registered by the backend in `care_im_wrapper/security/permissions.py`. The frontend names them in `src/lib/permissions.ts` — a mistyped string is not an error, it just hides the control forever.

| Slug | Context | Admin | Facility admin | Nurse | Staff | Doctor |
| --- | --- | :-: | :-: | :-: | :-: | :-: |
| `can_read_notification_event` | facility | ✓ | ✓ | ✓ | ✓ | ✓ |
| `can_create_notification_event` | facility | ✓ | ✓ | ✗ | ✓ | ✗ |
| `can_dispatch_notification_event` | facility | ✓ | ✓ | ✗ | ✗ | ✗ |
| `can_read_notification_template` | generic | ✓ | ✓ | ✓ | ✓ | ✓ |
| `can_manage_notification_template` | generic | ✓ | ✓ | ✗ | ✗ | ✗ |

## What each one gates

| Permission | Hidden without it |
| --- | --- |
| `can_create_notification_event` | "New notification" button; the create form shows a permission message instead |
| `can_dispatch_notification_event` | Dispatch button on the detail page, Dispatch item in the list's row menu |
| `can_manage_notification_template` | "Sync templates", activate/deactivate, and the editable variable-mapping form |

## Where the permission list comes from

Event permissions are facility-scoped, so screens read `facility.permissions` (fetched by `useCurrentFacility`).

Template permissions are generic and the admin routes have no facility, so those screens read `auth.user.permissions` instead.

Reads are not gated in the frontend. The backend enforces them, and `useFacilityAccessGuard` redirects when a facility fetch fails.
